# 模型 / 提供方配置架构设计

> 目标：把「用户要为 13 家平台各配一个 KEY」改成「按能力建实例，智能体各自挑一个实例」。
>
> 结论先说：**不要把服务商当成建模单位，要把「协议」和「能力」当成建模单位。**
> 服务商只是协议 + 默认 baseUrl 的一条预设。

---

## 一、现状问题（Novella 为什么不够灵活）

逐条对应代码位置，方便对照。

| # | 问题 | 位置 | 后果 |
| --- | --- | --- | --- |
| 1 | 提供方是**硬编码常量表**，13 家写死 | `src/core/config/model-providers.ts` `MODEL_PROVIDERS` | 想接一家没列进去的服务商（或自建中转站）无从下手 |
| 2 | **没有能力类型维度** | `src/core/ai/types/ai-core.ts` `ModelProvider` 是个 13 项字符串联合 | 「哪些能出图、哪些能做 TTS」靠 `AI_MODELS` 里手写的 `category` 数组隐式表达；提供方本身没有类型 |
| 3 | **没有「提供方实例」概念** | `MODEL_PROVIDERS: Record<ModelProvider, ...>` | 一家只能配一份 key。想同时接「官方」和「便宜中转站」做不到 |
| 4 | **没有「智能体 → 模型」绑定** | `src/core/services/agent/BaseAgent.ts` `AgentMetadata` | 元数据里根本没有 `model` / `provider` 字段，`BaseAgent` 也没有调 LLM 的能力。5 个内置 Agent 实际是空壳（只写黑板 + 打日志），只有 `CharacterDesignerAgent` 硬编码了 `provider: 'edge'` |
| 5 | **连通性校验是假的** | `model-providers.ts` `verifyModelApiKey()` | 只做正则格式校验，然后 `latencyMs = Math.random() * 20 + 15` 假装「连接畅通」。**从不发请求**，key 填错也能「校验通过」 |
| 6 | **存储命名混乱** | `hasAnyConfiguredModelProvider()` | localStorage 里同时存在 `ai_model_settings_${p}` / `api_${p}_key` / `novella_api_key_${p}` / `${p}_api_key` 四套命名，函数得把 17 个 key 全试一遍 |
| 7 | **自定义接口形同虚设** | `OpenAICompatibleStrategy` | 有抽象基类，但 `endpoint` 是子类**硬编码**的，没有用户填 baseUrl 的入口。设置页里 `image_models` / `video_models` / `audio_models` 是**伪 provider 条目**（名字叫「FLUX & 图像生成模型 API Key」），不是真服务商 |
| 8 | **模型列表是静态编造的** | `src/core/config/model-catalog.ts` `AI_MODELS` | 手写 26 个型号，含大量查不到的未来型号（`GPT-5.6 Sol`、`Gemini 3.6 Flash`、`Qwen 3.8-Max`）。跟真实 API 的 `/v1/models` 对不上，用户看到的选项和实际能调的模型是两回事 |
| 9 | TTS 与文本走**两套完全独立**的注册表 | `tts-provider-registry.ts` vs `provider-registry.ts` | 同样是「配 key + 选模型」，却是两套配置、两套 UI、两套存储 |

一句话：**Novella 把「服务商」当成了建模单位，而用户真正需要的是「能力」和「协议」。**

## 二、业界怎么做（5 个参照物）

### 1. Open WebUI —— 「协议中心，而不是服务商中心」

官方文档原话：*"Open WebUI is a protocol-centric platform… We focus on universal standards shared across dozens of providers."*

- 连接类型**只有两种**：`OpenAI` 和 `Anthropic`。Ollama / OpenRouter / vLLM / LM Studio / Groq / DeepSeek 全部作为 **「OpenAI + 自定义 Base URL」** 接入。
- 一条连接的字段：`Name`（可选显示名）、`Provider`、`API Type`（Chat Completions / Responses）、**`Base URL`（必填）**、**`API Key`**、**`Prefix ID`**、`Models`（可留空）。
- **模型发现**：`Models` 留空 → 调提供方的 `/models` 自动发现；填了就变成**白名单**（只暴露你写的那些）。文档明确指出「部分服务商不提供模型列表，需要在连接上手动填 Model IDs」。
- **`Prefix ID` 解决同名冲突**：两个连接都提供 `qwen3.6` 时，加前缀后显示为 `groq.qwen3.6`，请求发出去前再把前缀剥掉。
- 支持**单个模型启用/禁用**，以及**按任务分配模型**（"Titles, tags and autocomplete run on a model of their own; point them at a small one"）。

### 2. Dify —— 「提供方 → 模型实例 → 模型类型」三层

- **Model Provider**（供应商）→ 装上后填凭据，凭据由 Dify **真实校验**（"Dify validates the credentials before making the provider available"）。
- **Model**：提供方的模型随连接就绪，只有「没列出来的新模型 / 微调模型」才需要手动 `Add Model`。**手动模型可以有自己的凭据**（"A custom model relies on its own keys"）。
- **一个提供方可以有多份 key**：官方明确支持"keep development and production apart or spread usage across several accounts"。
- **Model Type** 是独立维度：LLM / Text Embedding / Rerank / Speech-to-Text / TTS。
- **默认模型按「用途」配置**：`Default Models` 面板里为 System Reasoning / Embedding / Rerank / STT / TTS **各设一个默认**；节点不指定时回退到默认。

### 3. SillyTavern —— Connection Profile（命名快照）

- Profile 保存的是「**API 类型 + 服务器 URL + Secret + 模型 + 各类 preset**」的**命名快照**，可以存很多个、一键切换。
- 关键限制写得很清楚：*"Profiles only save the selection in dropdown fields, without knowing anything about the underlying settings."* —— 即 profile 只是**引用**，不是副本。
- 有 slash command 管理：`/profile [name]`、`/profile-list`、`/profile-get`。

### 4. LibreChat —— Custom Endpoint + `models.fetch`

- 自定义端点对象：`name` / `apiKey` / `baseURL` / `models`（含 `default` 与 **`fetch: true`**）/ `modelDisplayLabel` / `directEndpoint` / `headers` / `dropParams`。
- `models.fetch: true` 时**真的去拉模型列表**，并且会把配置的 headers 一起转发给模型列表请求（管理员控制的 base URL 场景）。
- 支持多个自定义端点共存，按会话选择。

### 5. 本地 AI 漫剧链路（ComfyUI 系）—— 节点级绑定

2026 年的本地全开源漫剧方案（掘金/CSDN 多篇同源）典型分工：

| 环节 | 用什么 |
| --- | --- |
| 剧本 + 分镜脚本 | Qwen3.5-32B-Instruct（或 DeepSeek / 豆包 / 通义在线版） |
| 漫画分镜生成 | FLUX.1[dev] + 漫画 LoRA + IP-Adapter-FaceID-Plus / Reactor 锁脸 |
| 故事序列连贯 | StoryDiffusion 自定义节点 |
| 静图 → 唇同步视频 | LTX-2.3 |
| 后期 | 剪映 / DaVinci |

- 中枢是 **ComfyUI 节点工作流**，**每个节点各自指定自己的模型**（checkpoint / LoRA / adapter 互不相同）。
- 也就是说：**「一个流程里不同环节用不同模型」是这类工具的默认形态**，而不是高级功能。
- 它的短板正好是 Novella 的长板，反之亦然：ComfyUI 灵活但全是本地模型、没有统一凭据管理；Novella 有统一凭据管理但**没有环节级绑定**。

### 归纳：4 条共识

1. **协议 ≠ 服务商**。适配器按协议写（OpenAI 兼容 / Anthropic / 异步任务…），服务商只是「协议 + 默认 baseUrl」的预设。
2. **配置的最小单位是「实例」，不是「品牌」**。同一品牌可以有多份实例（不同 key / 不同中转站）。
3. **能力类型是独立维度**，且**按用途设默认**（Dify 的 Default Models）。
4. **模型列表要么真拉、要么手填，并且要能白名单过滤**；`Prefix ID` / 命名空间解决跨实例同名。

## 三、目标架构

### 3.1 三层

```
┌─ L1 协议 Protocol ─────────────────────────────────────────────┐
│ 代码里实现，用户不可改。按「是否有事实标准」分两档：              │
│                                                                │
│  ① 有事实标准的（直接写实现）：                                  │
│   openai-chat         Chat Completions —— 文本的事实标准         │
│   openai-images       POST /v1/images/generations —— 图像事实标准 │
│   openai-videos       POST /v1/videos —— Sora 格式，有标准化趋势  │
│   openai-speech       POST /v1/audio/speech —— 语音事实标准       │
│   edge-tts            免 key 本地兜底                            │
│                                                                │
│  ② 没有标准的（不写实现，写「声明式适配器」）：                    │
│   vendor-task         提交→轮询→取结果的通用引擎，行为由一份      │
│                       服务商描述符（JSON）驱动。覆盖可灵官方、     │
│                       火山方舟、MiniMax、智谱、Runway 等。         │
│                                                                │
│   （Anthropic / Gemini / Responses 按需再加，同样属于①）         │
└────────────────────────────────────────────────────────────────┘
```

> ⚠️ **视频生成没有事实标准**。详见 3.2 —— 这是本设计里唯一「不能靠协议收敛」
> 的地方，也是必须用声明式适配器的原因。
                              ↓ 用户选一个协议 + 填 baseUrl/key
┌─ L2 提供方实例 ProviderInstance ───────────────────────────────┐
│ 用户可建任意多个，是配置的最小单位。带 capability 标签。          │
│ 「DeepSeek 官方」「公司中转站 A」「本地 Ollama」都是实例。         │
└────────────────────────────────────────────────────────────────┘
                              ↓ 实例内选/拉一个具体模型 id
┌─ L3 模型引用 ModelRef ─────────────────────────────────────────┐
│ { providerId, modelId }。不落库为独立实体，只是引用。            │
└────────────────────────────────────────────────────────────────┘
                              ↓ 被谁用
┌─ 绑定层 SlotBinding ───────────────────────────────────────────┐
│ 智能体 / 流程环节 → 挑一个同 capability 的 ModelRef。             │
│ 多个槽位可以指向同一个 ModelRef（用户明确要的「共享 provider」）。 │
└────────────────────────────────────────────────────────────────┘
```

### 3.2 为什么视频不能用「一个协议吃所有」

> 本小节是对初版设计的**修正**：初版把 `async-task-video` 当成一个协议，这是错的。

异步任务只是「提交 → 轮询 → 取结果」这个**形状**相同，具体协议各家完全不一样。核对官方文档/示例后：

| 服务商 | 创建 | 查询 | 认证 | 任务 id | 状态枚举 | 取结果 |
| --- | --- | --- | --- | --- | --- | --- |
| 可灵官方 | `POST /v1/videos/text2video` | `GET /v1/videos/text2video/{task_id}` | **ak/sk 签 JWT (HS256)** | `data.task_id` | `submitted` / `processing` / `succeed` / `failed` | `data.task_result.videos[0].url` |
| 火山方舟 Seedance | `POST /api/v3/contents/generations/tasks` | `GET /api/v3/contents/generations/tasks/{id}` | Bearer | `id` | Ark 自有枚举 | 响应内 |
| MiniMax | `POST /v1/video_generation` | `GET /v1/query/video_generation?task_id=…` | Bearer | `task_id` | — | **先拿 file_id，再调一次换下载地址（两步）** |
| 智谱 CogVideoX | `POST /api/paas/v4/videos/generations` | `GET /api/paas/v4/async-result/{id}` | Bearer | `id` | — | 响应内 |
| OpenAI Sora | `POST /v1/videos` | `GET /v1/videos/{id}` | Bearer | `id` | `status` | **需另调 `GET /v1/videos/{id}/content` 取二进制** |
| 第三方中转站 | `POST /v1/videos/text-to-video` | `GET /v1/tasks/{TASK_ID}` | Bearer | — | `completed` | 响应内 |

六处分歧，任何一处都足以让「统一协议」破产：

1. **认证**：可灵官方要 ak/sk 签 JWT，不是 Bearer key —— 光这一条就不能只做 Bearer。
2. **查询传参**：MiniMax 走 query string，其余走路径参数。
3. **取结果**：MiniMax 要二次调用换下载地址，Sora 要单独的 `/content` 端点拿二进制。
4. **状态枚举**：`succeed` / `completed` / `SUCCESS` 各不相同。
5. **路径前缀**：`/v1/videos/…` / `/api/v3/contents/…` / `/api/paas/v4/…`。
6. **同一家两套**：可灵官方（JWT）与第三方中转站（Bearer）路径、认证都不同。

**对比另外三类**：文本有 OpenAI Chat Completions 这个事实标准，所以 Open WebUI 敢只做 2 种连接类型；图像有 `/v1/images/generations`；语音有 `/v1/audio/speech`。**视频没有。**

OpenAI 的 `/v1/videos`（Sora 格式）是当前最有标准化潜力的一家，第三方网关已在跟进，所以值得单列为协议 —— 但不能假设所有人都实现它。

**修正后的做法：声明式适配器**

保留一份「提交 → 轮询 → 取结果」的**执行引擎**（代码只写一次），每个服务商是一份**描述符**：

```ts
/** 逻辑字段名 → 上游字段名的映射，逻辑名固定，上游名随服务商变 */
interface VendorTaskDescriptor {
  id: string;            // 'kling-official' | 'volcengine-ark' | 'minimax' | 'zhipu-cogvideox' | ...
  label: string;

  // 认证：四种覆盖全部已知服务商
  auth:
    | { style: 'bearer'; header?: string }
    | { style: 'x-api-key'; header: string }
    | { style: 'query'; param: string }
    | { style: 'jwt-hs256'; accessKeyField: string; secretKeyField: string; ttlSec?: number };

  // 创建任务
  create: {
    method: 'POST';
    path: string;                        // '/v1/videos/text2video'
    body: Record<string, string>;        // 逻辑名 → 上游名，如 { prompt:'prompt', model:'model_name', durationSec:'duration' }
  };

  // 轮询
  poll: {
    method: 'GET';
    path: string;                        // '/v1/videos/text2video/{taskId}'
    query?: Record<string, string>;      // MiniMax 这类走 query 的填这里
    intervalMs: number;
    timeoutMs: number;
    statusPath: string;                  // 'data.task_status'
    statusMap: Record<string, 'pending' | 'running' | 'succeeded' | 'failed'>;
    errorPath?: string;                  // 'data.task_status_msg'
  };

  // 取结果（可选；MiniMax 的两步、Sora 的 /content 都靠它）
  fetchResult?: {
    method: 'GET';
    path: string;
    idFrom?: string;                     // 若结果里给的是 file_id 而非 URL
  };

  resultPath: string;                    // 'data.task_result.videos[0].url'
}
```

**逻辑字段名固定，上游名由 `body` 映射**，引擎只认逻辑名：

```
prompt / negativePrompt / model / durationSec / aspectRatio /
resolution / fps / seed / firstFrameImage / lastFrameImage
```

这样「新增一家视频服务商」= 加一份 JSON 描述符（或让用户自己在 UI 里填），**不用改代码**。内置一批，支持导入导出。

代价要说清楚：`body` / `statusPath` / `resultPath` 都是**字符串路径**，写错了只会在运行时报错。所以必须配一个「用最小请求试跑一次」的校验入口，把**上游原始响应**原样打出来给人看 —— 否则用户面对「找不到 data.task_id」无从下手。

**同样的思路适用于图像与 TTS**：它们有事实标准的路径，但**参数名各家仍有差异**（如尺寸字段 `size` vs `width/height`）。所以这三个能力都走「标准协议 + 可选字段映射覆盖」：

```ts
interface FieldOverrides {
  // 覆盖默认的逻辑字段 → 上游字段映射；留空即用协议默认
  body?: Record<string, string>;
  statusPath?: string;
  resultPath?: string;
}
```

文本因为标准最完整，通常不需要覆盖。

### 3.3 能力类型 Capability

沿用用户提的四类，并预留两类：

```ts
type Capability =
  | 'text'       // 剧本、分镜规划、人设、杂活
  | 'image'      // 分镜出图、锁脸参考图
  | 'video'      // 分镜转视频
  | 'tts'        // 配音
  | 'stt'        // 预留：字幕/对轴
  | 'embedding'; // 预留：素材检索
```

### 3.4 核心数据结构

```ts
// ---------- L2 提供方实例 ----------
interface ProviderInstance {
  id: string;                    // uuid，稳定标识（不是 provider 名！改名不影响绑定）
  label: string;                 // 用户命名：「DeepSeek 官方」「公司中转站」
  capability: Capability;        // 决定它出现在哪个选择器
  protocol: ProtocolId;          // 决定用哪个适配器
  baseUrl: string;               // 用户可填任意兼容端点
  apiKey: string;
  authStyle?: 'bearer' | 'x-api-key' | 'query' | 'none';
  extraHeaders?: Record<string, string>;   // 中转站常要的自定义头
  queryParams?: Record<string, string>;    // 少数服务商走 query 传参

  // 模型
  modelSource: 'auto' | 'manual';          // auto = 调 /models 拉取
  manualModels?: string[];
  modelFilter?: string[];                  // auto 拉取后的白名单（留空=全放行）
  prefix?: string;                         // 跨实例同名模型去重
  defaultModel?: string;

  // 能力级默认参数（不同能力参数差别很大，不强行统一）
  defaults?: {
    // text
    temperature?: number; maxTokens?: number;
    // image
    size?: string; n?: number; negativePrompt?: string;
    // video
    durationSec?: number; resolution?: string; fps?: number; aspectRatio?: string;
    // tts
    voice?: string; speed?: number; pitch?: number; format?: string;
  };

  enabled: boolean;
  lastProbe?: { at: number; ok: boolean; latencyMs?: number; error?: string };
  createdAt: number;
}

// ---------- L3 模型引用 ----------
interface ModelRef {
  providerId: string;
  modelId: string;
}

// ---------- 绑定层 ----------
type SlotId =
  // 内置流程环节
  | 'script.ingest'        // 剧本/小说识别拆解
  | 'script.rewrite'       // 剧本精修
  | 'character.design'     // 角色人设 + 锁脸 prompt
  | 'storyboard.plan'      // 分镜运镜规划
  | 'storyboard.image'     // 分镜出图
  | 'video.generate'       // 分镜转视频
  | 'audio.tts'            // 配音
  | 'util.fast'            // 标题/摘要/打标等杂活 → 指向便宜小模型
  // 用户自定义 Agent
  | `custom.${string}`;

interface SlotBinding {
  slot: SlotId;
  capability: Capability;              // 该槽位需要什么能力
  ref?: ModelRef;                      // 不填 = 回退该能力的默认实例
  overrides?: Record<string, unknown>; // 槽位专属参数覆盖
}

// ---------- 全局配置根 ----------
interface ModelSettings {
  schemaVersion: 2;                    // 迁移用
  providers: ProviderInstance[];
  capabilityDefaults: Record<Capability, ModelRef | undefined>; // Dify 的 Default Models
  slotBindings: Record<SlotId, SlotBinding | undefined>;
}

// ---------- 项目级覆盖 ----------
interface ProjectModelOverride {
  // 同一个工程可以换一套（比如「这集用便宜模型试跑」）
  slotBindings?: Partial<Record<SlotId, ModelRef | undefined>>;
  capabilityDefaults?: Partial<Record<Capability, ModelRef | undefined>>;
}
```

### 3.5 解析顺序（关键）

```
项目级 slotBindings[slot]
  ↓ 没有
Agent 自带 slotBinding
  ↓ 没有
项目级 capabilityDefaults[capability]
  ↓ 没有
全局 capabilityDefaults[capability]
  ↓ 没有
该 capability 下第一个 enabled 的实例的 defaultModel
  ↓ 没有
报错：「未为『分镜出图』配置图像提供方」
```

报错要**指名道姓说清缺哪个槽位**，而不是现在的「请先配置 API Key」。

### 3.6 模型发现

| 能力 | 拉取策略 |
| --- | --- |
| text / stt / embedding | `GET {baseUrl}/models`（OpenAI 标准，必发真请求）→ `data[].id` |
| image / tts | 先试 `GET {baseUrl}/models`（很多中转站有）；404/403 则回退到**该协议的内置候选名清单**（可编辑），并提示「该端点不支持模型列表，请手动填写或从候选中挑」 |
| video | 同上，但候选名清单来自**服务商描述符**（`VendorTaskDescriptor`，见 3.2）—— 因为连「模型叫什么」都随服务商变（`kling-v2-6` / `kling-3.0-omni` / `seedance-2.5`），没有跨家通用的名字 |

- 拉取结果**缓存**在实例上，配「刷新」按钮，不每次打开都请求。
- `modelFilter` 白名单过滤（Open WebUI 的做法）。
- 失败要**明确区分**：网络不通 / 401 未授权 / 404 无此端点 / 返回体不是模型列表 —— 现在的代码连请求都不发，这层信息全丢了。

### 3.7 凭据存储（已决定：不接系统 keyring）

- 现在：localStorage 明文 + 四套命名并存。
- 改为：**单一状态键** `aigv.modelSettings`，走 OTools 插件本地状态（`savePluginLocalStateValue`），带 `schemaVersion` 做迁移。
- **已决定不接系统 keyring**（Windows DPAPI / macOS Keychain 都不做）。理由：native 侧要额外写平台代码，收益不足以抵消维护成本；且插件本身已在用户本机、本地状态目录受操作系统账户隔离。
- 但**必须做两件事**：
  1. **把 README 的虚假宣传改掉** —— 上游宣称「API Key 加密存储于系统原生 Keyring」，实际代码里是 localStorage 明文。改成实话：「凭据存放在 OTools 插件本地状态（`~/.otools/local/aigv`），未做额外加密，请勿在共享账户的机器上使用」。
  2. **UI 上给出提示** —— 配置页明确标注「凭据以明文保存在本机」，让用户有知情权。
- 迁移函数要能吃掉现有四套命名，让老用户不用重填。

### 3.8 降低配置成本的其他手段

用户的核心痛点是「配太多 KEY」。除了分层，还可以：

1. **一个中转站 = 一个 key 覆盖多能力**：支持「从已有实例复制凭据」，同一 baseUrl + key 建 text/image/video 三个实例只需填一次。
2. **预设模板一键生成实例**：`MODEL_PROVIDERS` 那 13 家降级为模板（点一下预填 protocol + baseUrl + 常见模型名），而不是约束。
3. **能力继承**：图像/视频/语音实例可以「继承文本实例的凭据」，因为多数中转站同一 key 全通。
4. **未配置时的降级**：只配了 text 时，图像/视频槽位给出「用本地兜底（如 edge-tts / 内置占位）」而不是直接卡死。

## 七、网关层 vs 插件层：供应商集合放在哪里

### 7.1 ai-switch 已经在做这件事了

「能不能在 ai-switch 层面完成所有模型供应商的集合」—— 能，而且路已经铺了一半：

| 证据 | 位置 | 说明 |
| --- | --- | --- |
| `Provider { id, name, kind, base_url, model_config_json, target_options_json, secret_ref, status }` | `src-tauri/src/models/provider.rs` | 这已经是**「提供方实例」的雏形**：有 `kind`（类型）+ `base_url` + 凭据引用 |
| 完整 imagegen 模块 | `src-tauri/src/imagegen/`（commands / models / **protocol** / repository / service / storage / transport） | `protocol.rs` 做 **OpenAI Images ↔ OpenAI Responses ↔ Gemini** 三协议互转（请求体构造 + 响应解析） |
| `ImageMessage { model, upstream_model, member_id, cost_micros }` | `src-tauri/src/imagegen/models.rs` | 已经有**上游模型映射**与**计费** |
| ImageGen 已是独立左侧 TAB | `src/components/layout/AppLayout.tsx` | 受 `imageGenerationEnabled` 开关控制，归在「系统」分组 |

**更关键的是：ai-switch 的代理已经在路由 4 类 OpenAI 风格入口了**（`src-tauri/src/saas/proxy/mod.rs:79`）：

| 入口路径 | 对应 dialect | 状态 |
| --- | --- | --- |
| `POST /v1/chat/completions`（含 `/chat/completions`） | `openai` | ✅ 已有 |
| `POST /v1/responses`（含 `/responses`） | `openai-responses` | ✅ 已有 |
| `POST /v1/messages`（含 `/messages`） | `anthropic` | ✅ 已有 |
| `POST /v1/images/generations`（含 `/images/generations`） | 图像 | ✅ **已有** |
| `GET /v1/models` | 模型列表 | ✅ 已有 |

本地代理默认端口 **`127.0.0.1:19527`**（`route_proxy_service.rs` 的 `DEFAULT_ROUTE_PROXY_PORT`），客户端 baseUrl 就是 `http://127.0.0.1:19527/v1`。

所以 **ai-switch 其实已经是一个 OpenAI 兼容的多模态网关**（文本 + 图像），只是 README 把它讲成了「coding agent 配置切换器」，没把这一面说出来。它还支持按平台限制端点（如 `platform == "gemini"` 只允许 `images`）。

**结论修正**：文本与图像的「网关入口」已经存在，不需要新建。真正缺的只有：

| 缺口 | 现状 |
| --- | --- |
| `POST /v1/video/generations` + `GET /v1/video/generations/{task_id}` | ❌ 全新 |
| `POST /v1/audio/speech`（TTS） | ❌ 全新 |
| 视频/TTS 的上游适配 | ❌ 全新 |
| 异步任务表 + 轮询调度 + 回调 | ❌ 全新（图像是同步的，没有这套） |

所以 ai-switch 早就不是「只做 coding agent」了 —— 它已经有一个多模态模块的先例可以照抄，而且文本/图像的网关入口**已经上线**。

### 7.2 但有个取舍必须先说清楚

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| **A. 全放 ai-switch** | 用户只配一次，所有插件共享；协议适配一处维护；复用账号池 / 计费 / 日志 / SQLite | **插件从此依赖 ai-switch 常驻**；两个桌面应用互相依赖，装机成本上升；ai-switch 定位被拉宽 |
| **B. 全放插件** | 插件自包含，无外部依赖 | 用户在每个插件重复配 key（回到最初的痛点）；10+ 家视频适配每个插件维护一遍 |
| **C. 双层（推荐）** | 网关优先 + 直连兜底 | 需要维护两条路径 |

**推荐 C，而且它不需要额外的架构机制**：`ProviderInstance.baseUrl` 本来就允许指向任意端点 —— 指向 ai-switch 还是指向官方，插件不关心。「网关」不是一种特殊模式，**就是一个普通实例**。

- 装了 ai-switch：建 3 个实例（text / image / video），`baseUrl` 都填 ai-switch，key 填 ai-switch 的 token
- 没装：`baseUrl` 填官方端点
- 两种实例在「模型分配」表里混用也没问题

### 7.3 视频这类没有标准的入口：放网关，不放插件

三条理由：

1. **六处分歧是协议适配问题，不是业务流程问题。** 协议适配是网关的本职。
2. **new-api 已经证明可行**（见 7.5）。
3. **10+ 家适配放一处维护，所有插件受益。** 放插件里 = otools-aigv、compositor、未来的插件各维护一遍。

**插件侧只实现一个协议 `openai-videos`，契约对齐 new-api**：

- 用户用 ai-switch / new-api / OneAPI → 网关负责分发到各家
- 用户直连可灵官方（网关没覆盖）→ 走 3.2 的 `VendorTaskDescriptor` 兜底，但**只内置 2~3 家最常用的**，不再追求全覆盖

**插件真正独有的价值是漫剧业务流程**（素材解析 → 分镜 → 关键帧 → 转视频 → 配音 → 压制），不是协议适配。把协议适配下沉到网关，插件才能专注在流程上。

### 7.4 TTS 同理，但优先级不同

- TTS 有 `/v1/audio/speech` 这个事实标准（new-api 也按它中继），所以**不需要描述符就能先收敛**
- Edge TTS 免 key，可作本地兜底
- 只有火山 / 讯飞 / 阿里这类私有 TTS 协议才需要描述符，优先级低

### 7.5 new-api 是怎么做的（可直接照抄的契约）

**核心思路：按模态分端点给统一契约，供应商差异用 `metadata` 逃逸口吃掉。**

| 模态 | 统一端点 |
| --- | --- |
| 文本 | `/v1/chat/completions` |
| 图像 | `/v1/images/generations` |
| 视频 | **`/v1/video/generations`** + `GET /v1/video/generations/{task_id}` |
| 语音 | `/v1/audio/speech`（TTS）、`/v1/audio/transcriptions`（STT） |
| 音乐 | `/v1/audio/generations`（Suno） |

视频契约的具体字段：

```
POST /v1/video/generations
  model / prompt / duration / fps / height / width / image /
  metadata / n / response_format / seed / user
→ 201 { id, object: "video", model, created_at, task_id, status: "processing" }

GET /v1/video/generations/{task_id}
→ 200 { task_id, status: "processing"|"succeeded"|"failed", url, format, metadata, error }
```

**关键设计点**：

1. **`metadata` 是逃逸口**。可灵要 `negative_prompt` / `image_tail` / `seed`；即梦要 `req_key` / `image_urls` / `aspect_ratio`；Vidu 要 `resolution` / `movement_amplitude` / `bgm` / `callback_url` —— 全部塞进 `metadata`，不进主契约。
2. **状态枚举统一**成 `processing` / `succeeded` / `failed`（对比各家原始的 `succeed` / `completed` / `SUCCESS`）。
3. **响应统一**成 `{task_id, status, url, format, metadata, error}`，客户端不用管上游长什么样。
4. **客户端只认一个 baseUrl + 一个 `sk-` token**，永远看不到供应商差异。
5. new-api 内部用**渠道（Channel）**做聚合：一个渠道 = 一个上游账号 + 类型 + 模型列表，按模型名路由。它**不按模态分 TAB**，模态是渠道的属性。
6. 还有一个「无损渠道类型」的概念：客户端打某个端点时，命中该类型渠道才**不触发跨格式转换** —— 说明网关内部是**默认做格式转换**的。

### 7.6 关于「左侧新增一个视频 TAB」

**不建议一个模态一个 TAB。** ai-switch 左侧现在已经有 16 个 screen（Agents 分组 7 个 + 系统分组 5 个 + Accounts / Providers / Targets / Sessions / Batches / Imports / Logs / Vibe / OCR / Updates / About）。再加 Video / TTS / Music 会失控。

两个更重要的观察：

1. **模态不该只体现在导航上，而该体现在 `Provider.kind` 上。** ai-switch 的 `Provider` 已经有 `kind` 字段 —— 把它从「coding agent 平台」扩成「模态 + 协议」（`text:openai` / `image:openai` / `video:kling` / `tts:volcengine`），模态就成了渠道的属性。**这正是 new-api 的做法**：不按模态分 TAB，按渠道配，模态是渠道属性。
2. **ImageGen 现在的位置其实是错位的。** 它归在「系统」分组、跟 MCP / Skills / Settings 放一起，但它本质是「用模型生成内容」，跟 Accounts / Providers 是一类。

**建议的收敛**：

- 把 `ImageGen` 升级为统一的 **「生成」`Generate`** 一个 TAB，内部按模态切 tab（图像 / 视频 / 音频），共用会话、资产库、历史、计费
- 左侧**净增 0 个 TAB**（替换而非新增），未来加模态也不改导航
- 模态能力由 `Provider.kind` 声明，`Settings` 里的开关从 `imageGenerationEnabled` 扩成能力位掩码

### 7.7 要在 ai-switch 里动的地方

| 项 | 现状 | 要做 |
| --- | --- | --- |
| 数据模型 | `Provider { kind, base_url, model_config_json }` | `kind` 语义扩为「模态:协议」；`model_config_json` 加 `capability` / `modelFilter` / `prefix` |
| 协议层 | `imagegen/protocol.rs`（3 协议互转） | 新增 `videogen/protocol.rs`（`/v1/video/generations` 契约 + 各家适配）、`tts/protocol.rs`（`/v1/audio/speech`） |

### 7.8 产品问题（已决定）

**已决定：选 (b)，ai-switch 扩成完整多模态网关。**

所以这一章里 7.6 / 7.7 的内容都要做：导航收敛、会话模型、计费单位、异步任务表。

但要注意一个**顺序上的好处**：因为 ai-switch 的 `/v1/chat/completions`、`/v1/responses`、`/v1/messages`、`/v1/images/generations` 入口**已经存在**，插件侧的文本与图像链路可以**立刻**接上 ai-switch，不必等网关的视频/音频做完。也就是说：

```
P1（插件：数据模型+存储+迁移）
P2a（插件：openai-chat）  ← 现在就能指向 http://127.0.0.1:19527/v1 跑通
P2b（插件：openai-images / openai-speech / edge-tts）
     ↑ 图像已经能走网关；语音要等网关加 /v1/audio/speech
P2c（插件：openai-videos + 描述符）  ← 等网关加 /v1/video/generations
```

**两条线可以并行**：插件侧先做（不依赖网关改动），网关侧的视频/音频同步推进，谁先好谁先接。

**网关侧的最小改动清单**（在 ai-switch 里）：

| 优先级 | 项 | 说明 |
| --- | --- | --- |
| P0 | 把 `/v1/chat/completions` + `/v1/images/generations` 的能力**写进 README 与 UI** | 现在这一面没暴露出来，用户不知道它能当通用网关用 |
| P1 | `Provider.kind` 语义扩为「模态:协议」 | 现在是 coding agent 平台语义 |
| P1 | 新增 `POST /v1/audio/speech` + Edge TTS（免 key）适配 | TTS 有事实标准，最容易 |
| P2 | 新增 `videogen` 模块（照抄 imagegen 结构）+ `/v1/video/generations` 契约 | 对齐 new-api |
| P2 | 异步任务表 + 轮询调度 + `callback_url` 回调 | 视频是异步的，图像是同步的，这套全新 |
| P3 | 计费单位扩展（视频按次/秒、TTS 按字符） | 现在 `cost_micros` 是按张 |
| P3 | 导航：`ImageGen` → 统一 `Generate`，内部分模态 | 净增 0 个 TAB |

## 八、协议清单：到底要做几个

### 8.1 先定义「协议」是什么

本方案里「**协议**」= 一套 **端点路径 + 认证方式 + 请求体形状 + 响应体形状**。一个协议适配器就是一段代码：把统一逻辑字段翻译成上游要的格式，再把上游响应翻回统一形状。

**两侧都有协议，别混**：

- **入口协议** —— 网关对外暴露的，**插件只认这一层**
- **上游协议** —— 各家官方要的，**网关负责适配**

### 8.2 ai-switch 侧（入口协议）：已有 4 个，要做 2 个

| 入口 | 状态 | 覆盖谁 |
| --- | --- | --- |
| `POST /v1/chat/completions` | ✅ 已有 | 所有 OpenAI 兼容上游 |
| `POST /v1/responses` | ✅ 已有 | OpenAI 新版 / Codex |
| `POST /v1/messages` | ✅ 已有 | Anthropic |
| `POST /v1/images/generations` | ✅ 已有 | 图像 |
| `GET /v1/models` | ✅ 已有 | 模型列表 |
| `POST /v1/video/generations` + `GET /{task_id}` | ❌ 要做 | 视频（对齐 new-api 契约） |
| `POST /v1/audio/speech` | ❌ 要做 | TTS |

### 8.3 插件侧（otools-aigv）：**这就是「协议先做几个」的答案**

**建议 6 个，分三批：**

| 批次 | 协议 | 端点 | 覆盖谁 | 为什么放这批 |
| --- | --- | --- | --- | --- |
| **P2a** | `openai-chat` | `POST /v1/chat/completions` | OpenAI / DeepSeek / 通义 / 智谱 / Kimi / 混元 / 豆包 / Ollama / vLLM / LM Studio / OpenRouter / OneAPI / NewAPI / **ai-switch** | 现在所有 Agent 都调不了 LLM，这是最大痛点；一个协议覆盖 90% 场景 |
| **P2b** | `openai-images` | `POST /v1/images/generations` | OpenAI 图像 / 各种中转 / **ai-switch（入口已有）** | 图像有事实标准 |
| **P2b** | `openai-speech` | `POST /v1/audio/speech` | OpenAI TTS / 中转 / ai-switch（待加） | 语音有事实标准 |
| **P2b** | `edge-tts` | 本地 / 免 key | 无 key 兜底 | 让「一个 key 都没配」也能出声 |
| **P2c** | `openai-videos` | `POST /v1/video/generations` + `GET /{task_id}` | ai-switch（待加）/ new-api / Sora | 对齐 new-api 契约 |
| **P2c** | `vendor-task` | 描述符驱动（见 3.2） | 直连可灵官方（JWT）/ 方舟 / MiniMax / 智谱 / Runway | 网关没覆盖时的兜底，**内置 2~3 家即可** |

### 8.4 暂时不做的 3 个（以及为什么）

| 协议 | 为什么可以先不做 |
| --- | --- |
| `openai-responses` | 主要给 Codex 用；ai-switch 已能把 `/v1/chat/completions` 桥接到 Responses 上游 |
| `anthropic-messages` | 同理 —— 用户在 ai-switch 里配好 Claude 官方账号，网关会把 `/v1/chat/completions` 桥接成 `/v1/messages` |
| `google-generateContent` | 同理，网关已支持 gemini dialect |

**这是「网关优先」决策换来的最大收益：插件侧协议数从 8 降到 6，而且把三个最容易出错的非 OpenAI 协议全砍掉了。**

只有一种情况需要补它们：用户**直连官方** Claude / Gemini 且不走任何网关。这种场景可以先用 `openai-chat` + 中转站顶住，真有人要再补。

### 8.5 判断标准（以后加协议看这条）

> **只有当「上游没有 OpenAI 兼容端点」且「网关也不覆盖」时，才需要新协议。否则一律复用 `openai-*`。**

按这个标准，未来可能要加的只剩：

- `vendor-tts` —— 火山 / 讯飞 / 阿里私有 TTS，复用 `vendor-task` 引擎（不是新引擎，只是多一份描述符）
- `azure-openai` —— 如果要用 Azure 的 deployment 语义（路径和参数名都不同）
